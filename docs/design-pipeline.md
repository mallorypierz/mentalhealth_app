# Part 1 design proposal and initial prototype — October 15, 2026

## Scope and design
The developer authorized the initial Vue prototype and local Vue/Vite installation after confirming there was no source code. This is an in-memory frontend demonstration, not the later FastAPI/SQLite/RAG implementation. No provider calls, credentials, database, clinical assessment, or persistence are present.

The prior Figma reference is https://www.figma.com/design/3fMOXNlHnM4ebWaFKI0CXi/Assignment-3?node-id=1-6. MCP returned a blank white Activity frame and screenshot. This implementation follows the README, not a populated Figma design. No capture or Figma revision has occurred. The pasted class instructions still use a selected-frame placeholder.

Chosen flow: entry → six-cycle breathing practice → stopped/completed result → optional history. Direct start avoids typing and model delays. Muted green surfaces, high-contrast text, a single primary action, and a still-cue alternative support the README's class principles. A simple history table shows activity without interpreting wellbeing. Tradeoff: a fixed 60-second duration and plain session records offer less customization and visual analysis. The sidebar becomes a compact navigation row on narrow screens.

## Responsibility and behavior contracts
- `frontend/src/exercise.js`: framework-independent controller for timing and phase; LatestRequest guards stale asynchronous results.
- `frontend/src/App.vue`: Vue views, interactions, in-memory session records, mock introduction, support panel, focus behavior.
- `frontend/src/style.css`: layout, visual styles, keyboard focus, responsive rules, motion.
- `backend/` and `data/`: reserved for later work; no API/data contracts are claimed implemented.

Start initializes a new ID and monotonic timer. Six cycles each contain 4 seconds in and 6 out. Total planned guided time is 60 seconds; entry reading/setup and voluntary pauses are separate. A worked example: start, practice 5 seconds, pause for 20 seconds, resume for 5 seconds, stop → one stopped record with 10 active seconds. Whole seconds are rounded down for display. Completion caps duration at 60 seconds. Restart clears the old interval. Pause excludes subsequent elapsed time; support opens paused, disables Resume until closed, and never resumes automatically. Stop remains available in the panel and exercise. Finished sessions are appended once to in-memory history; one labeled fictional fixture is present. Refresh recreates the fixture and clears tab sessions/preferences.

Mock introduction modes: success returns reviewed fixed app instructions after 500ms; failed shows an explicit error and retry; delayed waits 8 seconds. Loading disables duplicate requests. Mode changes and starting practice cancel the pending timer and invalidate its request version. Even an already-arriving stale result cannot apply. There is no saved conversation or claimed AI integration.

US/territories crisis-resource details were obtained from the required helpline lookup tool on October 15, 2026. Resource links are independent of mock responses. Calls/text/chat were not exercised; the demo itself is not monitored. Other countries are not covered by this initial panel.

## Planned architecture and behavior (Part 1 proposal)

Everything in this section is **planned, not implemented**, unless explicitly labeled current. Endpoint names, record fields, and limits below are proposed implementation contracts, not claims that services or tables exist. The present prototype runs entirely in Vue memory; `backend/` and `data/` are empty. The earlier flow diagram and research mapping remain the design basis.

### Responsibilities and request flow

| Layer | Responsibility | Boundary |

Current file ownership remains `frontend/src/exercise.js` for timing/stale-request protection, `App.vue` for UI and temporary records, and `style.css` for presentation. Proposed backend modules would separate `routes/`, `controllers/`, `models/`, `repositories/`, and `services/` (provider/retrieval). These folders have not been created; exact files will be recorded when implemented.

Planned ordinary flow: **Vue event → FastAPI validation and controller → repository → SQLite transaction → typed JSON with record IDs and persistence status → Vue view.** History reads and preference loads do not need the model. Start initiates local practice immediately; saving can occur alongside it. If saving fails, practice/support remain usable, and the UI must show an unsaved record rather than success.

Only the backend loads provider settings explicitly from ignored `backend/.env`; an example file will contain variable names without credentials. A configuration check reports presence, never values, and cannot be mistaken for a successful provider call. No environment file or credentials are created by this proposal.

### Application-owned rules and model limits

Application code fixes six 4/6 cycles, valid state transitions, timers, pause accounting, cancellation, Stop, completion, and history saving. Opening support pauses running practice; closing it does not resume. Explicit Resume is required and remains disabled while support is open. Stop works even while a request is pending, fails, or times out. The model cannot force an exercise, change its pace, hide support, mark completion, or save records directly.

The model may explain how to start/stop, restate reviewed breathing instructions, or describe a saved session's recorded duration/status with its ID. It must distinguish a person's explicit report from observed activity and interpretation. A stopped session means only that the session stopped; it does not establish distress, improvement, preference, or diagnosis. With no relevant records, it says the history is insufficient rather than inventing an earlier practice. Optional chat stays outside the timed sequence. No raw generated text becomes executable markup or application commands.

### Proposed records, identifiers, and relationships

Use stable UUIDs for entity identifiers, server-assigned UTC timestamps for saved events, and explicit ordering rather than sorting by timestamps alone. A backend-resolved fictional demo-user scope owns all records. It is not a production authentication system; a client-supplied user ID must not grant access to another scope.

| Record | Proposed fields and relationships | What the person can review |
| --- | --- | --- |
| Demo user | `demo_user_id` primary key; fictional display label. Parent of conversations, sessions, preferences, and requests. | Clearly labeled fictional profile/context; no diagnosis or inferred emotional state. |
| Conversation | `conversation_id` primary key; `demo_user_id` foreign key; `created_at`, `updated_at`, optional neutral title. | Conversation list, dates, and selected conversation history. |
| Message | `message_id` primary key; `conversation_id` foreign key; `request_id` foreign key; `role` user/assistant; `content`; `created_at`; per-conversation `sequence`; request status. Unique sequence within a conversation and unique user/assistant slot per request. | Actual submitted text and actual reply, roles, order/time, IDs, and pending/failed/saved state. No fabricated assistant row when generation fails. |
| Exercise session | `session_id` primary key; `demo_user_id` foreign key; optional same-owner `conversation_id`; fixed `skill_key`; `started_at`, `ended_at`; `active_duration_ms`, `paused_duration_ms`; status in-progress/stopped/completed/interrupted; `is_fixture`; revision. | Session table with time, duration, status, ID, and fixture label. Completed/stopped are distinct; no emotional or clinical score. |
| Preference | `preference_id` primary key; unique `demo_user_id`; explicit `motion_choice` still/animated; `remember_choice`; `updated_at`; revision. Persist only with opt-in. | Current choice, effective mode, whether it is saved, and change/forget controls. Session-only choices stay in Vue memory. |
| Request bookkeeping | `request_id` primary key; scope, conversation and input fingerprint; status, attempt number, safe error code, relevant retrieved record IDs, provider-call count, timestamps. | User-facing request/save status and cited record IDs; not credentials, hidden provider reasoning, or unrestricted SQL/log dumps. |

Foreign keys and same-owner checks enforce relationships, including session links to conversations. Start/stop timestamps describe occurrence, not a reliable substitute for active duration because pauses are excluded. In-progress/interrupted records are proposed for honest recovery; the current prototype stores only terminal in-memory sessions and loses them on refresh. Retention, deletion, and interruption-recovery details remain open below.

### Proposed HTTP/JSON contracts and failure behavior

All routes below are **unimplemented**. Typed request/response models should limit text lengths, enforce enum values and UUIDs, reject invalid durations, and bound pagination. Success includes IDs and `persistence: saved` only after commit. Use a consistent error envelope: `error.code`, plain `error.message`, `retryable`, `request_id`, and the known persistence state. Suggested statuses: 422 invalid input; 404 missing/out-of-scope record (no existence leak); 409 conflicting retry/revision; 429 call budget reached; 503 unavailable database/configuration; 504 provider timeout. Empty history is a successful empty list, not an outage.

| Method / proposed path | Validated input | Successful output / special failure rule |
| --- | --- | --- |
| POST `/api/conversations` | Client-generated conversation ID and operation ID. | Saved conversation ID/time; identical retry returns existing record. |
| POST `/api/conversations/{id}/messages` | Nonempty bounded content and stable request ID; backend resolves owner. | User message ID, actual assistant ID/content if successful, retrieval outcome, cited IDs, request status and accurate persistence. May return 202 pending with a status URL; failure never invents a reply. |
| GET `/api/requests/{request_id}` | Scoped request ID. | Pending/succeeded/failed state and persisted IDs; safe recovery after an uncertain network response. |
| POST `/api/requests/{request_id}/retry` | Failed request ID and a unique retry operation ID. | Resume one failed attempt without inserting the user message again. Same retry operation cannot cause a second provider invocation. |
| GET `/api/conversations` and GET `/api/conversations/{id}/messages` | Bounded cursor/limit; conversation ID where applicable. | Ordered scoped records with IDs, timestamps, statuses, and next cursor. |
| PUT `/api/sessions/{session_id}` | Fixed skill, occurrence timestamps, bounded durations, status, optional conversation ID, expected revision and operation ID. | Saved session/revision. Repeated finalization returns the same result; conflicting changes to a terminal record fail rather than duplicate it. |
| GET `/api/sessions` | Bounded cursor/limit and allowed filters. | Saved session rows including fixture and interruption labels. |
| GET `/api/preferences/motion` | Backend-resolved scope. | Saved explicit choice or no saved preference. |
| PUT `/api/preferences/motion` | Explicit motion choice, opt-in, operation ID, expected revision. | Saved choice/revision only after commit. On failure, current session display may still change with an unsaved label. |
| DELETE `/api/preferences/motion` | Explicit forget action with operation ID. | Confirmed removal after commit; failures cannot claim the stored preference was forgotten. |

Conversation saving uses separate short transactions around network calls: first persist the submitted user message and pending request together; then perform provider work without holding a write transaction; finally persist the actual reply and succeeded status together. If the first transaction fails, do not call the provider. If generation fails, retain the saved user message and mark the request failed, with no assistant message. If final persistence fails, return an honest save failure; a generated reply must not be presented as saved. A retry after an uncertain response first reads request status. If a generated reply was never durably stored and cannot be recovered, disclose that loss rather than reconstructing it as the original reply.

Use one in-flight generation per conversation initially. Unique operation IDs, input fingerprints, database constraints, and atomic state transitions prevent duplicate messages/sessions and reject reuse of an ID with different content. Vue also disables duplicate sends and invalidates older callbacks when starting practice or changing context. Ignoring a late UI response does not claim to undo a backend call or a reply already saved; any saved result remains reviewable later in conversation history.

### Planned SQL-based retrieval-augmented generation

1. **Persist and scope the question.** The backend determines the current fictional user/conversation, validates the question, and records its request. Provide the query-planning model only a reviewed schema description and question. Schema describes fields/relationships; it is not retrieved history. The model has no SQLite connection.
2. **Ask for a query proposal, not executable authority.** Return one bounded SQL proposal and proposed filter values in a structured response. Counts and time limits below are draft constraints to test, not installed configuration.
3. **Validate with a narrow structural allowlist.** Parse the complete SQL and reject extra statements, comments used to hide extra input, writes, DDL, PRAGMA, ATTACH, extension loading, arbitrary functions, SQLite metadata, and access to request/secrets tables. Initial grammar should allow a simple SELECT from one approved retrieval view with named permitted fields, supported comparisons, ordering, and LIMIT; reject joins, subqueries, CTEs, UNION, wildcards, and unsupported syntax until specifically required and tested. Checking only a SELECT prefix or using a regex is insufficient. Fail closed on parser uncertainty.
4. **Enforce scope independently.** Construct a backend-owned outer query over approved projections scoped by bound `demo_user_id` and, for messages, current `conversation_id`. Re-emit only validated expressions from the parsed tree; never execute the model's raw string. Model output cannot supply or weaken ownership predicates. Session history may span that same fictional user's sessions only. Bind all data values; identifiers must come from a fixed allowlist. Use a separate read-only SQLite connection and an authorizer that denies writes and access outside permitted reads/functions as defense in depth.
5. **Bound execution and context.** Proposed initial limits: 20 returned rows, a 100ms query execution budget using a progress/timeout guard, and 8,000 characters of serialized context including field descriptions. Enforce limits in application code even if the proposal asks for more. Mark truncation so a partial result is not described as complete history. Keep retrieval separate from normal application-owned writes.
6. **Generate a grounded answer in a second call.** Send only relevant allowed records, their IDs/field meanings, and versioned reviewed skill/app context. Delimit stored text as data, not instructions. A stored message saying to ignore rules cannot override application policy. Require citations to supplied IDs; verify cited IDs belong to the retrieved set before accepting output. Citation membership alone does not prove the wording is accurate, so test groundedness too. The model cannot insert/update/delete records.
7. **Save the actual response through the normal transaction.** Return it to Vue only with truthful persistence status. Both planning and answering count toward the call budget, including unsuccessful attempts. Mock tests make no paid calls.

Distinguish `empty` retrieval (no matching records), `rejected_query`, `database_error`, `provider_error`, and `truncated` context. For empty retrieval, a successful answer can explicitly state there is no matching history and explain reviewed app content. Rejected SQL or a failed database call must not be relabeled empty history; return a distinct retryable/nonretryable status and keep Start/support usable. Proposed provider constraints are finite 15-second timeouts per call, an overall request deadline, response schema/size validation, and no hidden automatic retries. Any live-test budget must be agreed first and must not exceed the coursework cap of 50 model calls per session.

**Worked fictional example:** “What happened in my last practice?” → validated read of the latest owned session → record `session-demo-01` (illustrative ID, not an actual UUID/record), stopped after 23,000 active milliseconds → answer describes a stopped 23-second practice and cites the returned session ID. It does not say the person felt worse or improved. An empty result produces an honest lack-of-history response. A proposed DELETE is rejected before SQLite execution and before answer generation.

### Explicit personalization and effective motion

The developer selected an optional “Remember my display choice” control and confirmed that **system reduced motion always overrides a saved animated choice**. Proposed effective-mode order: system reduced motion → explicit current-session choice → opted-in saved choice → documented default. A system-imposed still cue must be explained rather than displaying a misleading animated selection as active. Live system-setting changes should not restart the exercise timer.

Remembering is optional and outside the timed exercise. Show session-only, saving, saved, or failed-to-save status; allow changing the choice and an explicit forget action. A failed preference load uses a disclosed default/session choice and never blocks practice. Forgetting must acknowledge database removal only after success. Exactly where the control appears and whether unchecking it immediately deletes an existing choice remain open. Saving a display preference is not evidence of a preferred skill, emotional state, or diagnosis.

### Proposed handling of crisis-related input

**Current limitation:** the prototype has no free-text chat or crisis-text detection. It provides an independent support panel; the selected persistent bottom bar is not implemented.

For later free-text chat, propose a small reviewed application-owned cue check for explicit crisis-related wording. A match would add a brief, non-diagnostic acknowledgment, explain that this coursework app is not monitored, and offer the existing Crisis support action. It would not force practice, promise safety, contact anyone, claim risk assessment, or let the model invent crisis resources. Exact wording and cue coverage require review before implementation; this is a proposal, not a developer-approved clinical protocol. The generative model should stay within reviewed app/skill content and route crisis-related discussion toward the same verified resource panel rather than improvising therapeutic advice.

A keyword/cue rule can miss indirect wording, different languages, sarcasm, spelling variations, and context; it can also flag fictional discussion or quotations incorrectly. A no-match is never proof of safety. A model can likewise miss or misinterpret a message, fail, time out, or be misconfigured. Therefore support remains visible and available independently of detection, model results, a questionnaire, database state, or paid-call budget. Users may open or decline it without being classified. Keep resource content application-owned, region-labeled, and reviewed; do not guess geography from behavior. Test only fictional inputs and never initiate real crisis-service contacts as a software test.

### Timing definition and validation plan

The planned guided sequence is **six × (4 seconds inhale + 6 seconds exhale) = 60 seconds** at the intended pace. Measure from the first actionable exercise instruction to the end of the final exhale, including any application delays inside that interval. Record entry/setup separately: reading the overview, changing display settings, and requesting the optional introduction are outside the timed sequence. The person need not type or confirm each breath; the timer cues the intended pace and does not measure actual breathing.

Subtract voluntary pause intervals and time spent accessing support, without double-counting overlapping pauses. After support closes, time remains excluded until the person explicitly resumes. No response deadline is imposed on the person. Completion offers a result rather than forcing an exit. Saving or optional chat cannot be inserted between breathing phases.

**Current evidence:** the timing controller caps active time at 60,000ms and previous browser checks observed a completed 60-second result; unit tests checked phase boundaries and pause exclusion. The counter alone cannot prove that rendering delays did not lengthen the experienced exercise. Future verification should compare an external elapsed-time observation with displayed cues, measure entry/setup separately, and test interruptions and delays. Do not subtract ordinary application stalls to satisfy the 90-second limit. Browser throttling/device sleep may skip visible cues under the current clock logic; this remains a limitation, not a verified completion experience.
